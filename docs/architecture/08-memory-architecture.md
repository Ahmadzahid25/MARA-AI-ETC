# Phase 8 — Memory Architecture

## 8.1 Why six distinct kinds, not one "memory" blob

Collapsing memory into a single store (e.g., "everything in the LLM context window" or one generic key-value table) breaks retention, access-control, and retrieval requirements that differ sharply by kind: audit records must be immutable and retained regardless of workflow lifecycle, conversation history is per-officer and should not silently leak across sessions, and knowledge memory is shared and versioned independently of any single conversation. `services/memory_service` ([03-repository-structure.md](03-repository-structure.md)) exposes these as six distinct, separately access-controlled namespaces over the same underlying Postgres store ([04-technology-stack.md](04-technology-stack.md)) — one physical database, six logical, independently governed memory kinds.

## 8.2 Memory kinds

| Memory kind | Contains | Scope | Retention | Indexing / retrieval | Versioning | Security |
|---|---|---|---|---|---|---|
| **Conversation Memory** | Officer↔system chat turns, including agent-facing tool-call/observation messages within one session | Per conversation session, owned by the initiating officer | Retained per MARA records-retention policy (default 7 years, configurable per document classification); soft-deletable by officer for non-substantive chat, never for anything referenced by an approved workflow | Chronological + full-text search on message content | Append-only; edits create a new turn, never mutate history | Row-level security keyed to officer ID; Compliance/Auditor roles can read with justification logged |
| **Task Memory** | Per-agent-task inputs, outputs, confidence scores, provenance | Per workflow task instance | Retained for the life of the workflow instance plus the same records-retention period as Conversation Memory | Keyed by workflow ID + task ID; queried by Supervisor/Validation stage | Immutable once a task completes; a re-run creates a new task record, preserving the prior attempt | Scoped to the workflow's participating officers/roles |
| **Long-term Memory** | Cross-workflow officer/agent learnings — e.g., an officer's standing preferences, an agent's calibration history (how often its confidence scores were subsequently overridden) | Per officer or per agent-role, spans workflows | Retained indefinitely, reviewable/purgeable on request (PDPA right-to-erasure path where applicable to personal data) | Structured key-value + periodic batch analysis (e.g., confidence calibration reports feeding Phase 12 observability) | Versioned snapshots, not raw overwrite, so calibration drift is analyzable over time | Personal-preference data classified and access-controlled the same as any other PII under [11-security-architecture.md](11-security-architecture.md) |
| **Knowledge Memory** | Policy documents, precedent, product terms, market data cache — the corpus backing RAG retrieval | Organization-wide, not per-officer | Governed by document lifecycle policy ([09-knowledge-architecture.md](09-knowledge-architecture.md)), not by workflow lifecycle | Vector similarity + metadata filter, served by `services/knowledge_service` | Full version history per source document; retrieval always resolves to the currently-approved version unless a workflow explicitly pins a prior version for reproducibility | Document-classification-based access control; sensitive corpora (e.g., internal risk criteria) restricted by role |
| **Shared Memory** | Live, in-flight workflow state — the Shared Memory referenced throughout [05-agent-architecture.md](05-agent-architecture.md), where agents publish outputs for downstream agents to consume within one workflow instance | Per workflow instance, read/write by participating agents only | Same lifecycle as Task Memory — persists with the workflow, not ephemeral | Keyed by workflow ID; this **is** the LangGraph checkpoint state (Phase 7), not a separate store agents must remember to sync | Overwritten only by the producing agent's own re-run; other agents read the latest published version | Scoped strictly to the workflow's declared agent participants — an agent outside the graph cannot read another workflow's Shared Memory |
| **Audit Memory** | Every tool call, agent dispatch, approval/rejection/correction, escalation, and permission check, platform-wide | System-wide, append-only | Immutable, retained per the longest applicable regulatory/audit retention requirement — never deleted, never edited, not even by administrators; table-partitioned by time range from day one so this high-volume append-only table doesn't degrade hot-path queries elsewhere in the same Postgres instance | Time-range + workflow-ID + actor-ID indexed; this is what the Audit Service queries ([05-agent-architecture.md](05-agent-architecture.md) §5.11.3) | N/A — write-once by construction | Written by `supervisor_service`, Tool Runtime, and Approval Service **independently**, so no single compromised component can suppress its own record (see [02-system-architecture.md](02-system-architecture.md), [11-security-architecture.md](11-security-architecture.md)); read access restricted to the Auditor role |

## 8.3 Retention in practice

Retention is enforced at the `memory_service` API layer, not left to callers to remember: every write to Conversation, Task, or Long-term Memory carries a computed retention/classification tag at write time, derived from the workflow's data classification (see [11-security-architecture.md](11-security-architecture.md)) — an officer or agent cannot write memory without one. Audit Memory has no delete path in the API surface at all; there is no code path, privileged or otherwise, that removes an Audit Memory row, which is what makes "was this ever deleted" an unanswerable-by-design question rather than a policy promise.

## 8.4 Indexing and retrieval

- **Structured lookups** (Task/Shared/Audit Memory): indexed Postgres queries by workflow ID, task ID, actor ID, and time range — these are operational/audit queries, not semantic search, and are served directly from Postgres rather than routed through the vector store.
- **Semantic retrieval** (Knowledge Memory): pgvector similarity search behind `services/knowledge_service`, detailed fully in [09-knowledge-architecture.md](09-knowledge-architecture.md).
- **Conversation search**: Postgres full-text search is sufficient at expected volume; semantic search over conversation history is deferred rather than speculatively built — see [16-future-expansion.md](16-future-expansion.md) if usage data later justifies it.

## 8.5 Versioning

The versioning need differs by kind and is handled accordingly rather than with one generic "version" column everywhere: Knowledge Memory needs full document version history because policy changes and a workflow must be able to cite exactly which policy version it checked against; Task/Shared Memory need re-run history (not edit history, since a task is immutable once complete) so a Validation-triggered re-run doesn't destroy evidence of the first attempt; Long-term Memory needs snapshot history specifically to support confidence-calibration analysis over time; Audit and Conversation Memory are append-only by nature and need no separate versioning concept at all.

## 8.6 Security summary

Full detail in [11-security-architecture.md](11-security-architecture.md); the memory-specific points worth stating here: every memory read is authorized against the requesting principal's role **and** the specific workflow/conversation scope (an officer cannot read another officer's in-flight Loan Assessment Shared Memory by default), Audit Memory access is logged even for Auditor-role reads (auditing the auditors), and cross-workflow reads (Long-term Memory, Audit Memory) require an explicit elevated role rather than being an emergent side effect of broad database access.
